# TimerMeet UI design notes

## Color palette (defined at the top of `timermeet_app/main_window.py`)

| Constant | Value | Use |
|---|---|---|
| `WINDOW_BG` | `#15171c` | Root window background |
| `PANEL_BG` | `#1c1f26` | Header/form/summary panel backgrounds |
| `FIELD_BG` | `#252a33` | Entry/OptionMenu/Textbox backgrounds |
| `BORDER` | `#333844` | Field border/highlight |
| `TEXT` | `#f2f3f5` | Primary text |
| `MUTED` | `#9aa1ac` | Secondary text (hints, labels) |
| `SUBTLE` | `#767d88` | Tertiary text (recurrence line) |
| `ACCENT` / `ACCENT_HOVER` | `#3b82f6` / `#2563eb` | Primary action buttons (Save, Open Teams); also the "week view" discoverability button in `full_view`/`calendar_view`'s header (v2.10.0, see `_build_header`) -- the one non-"primary-action" use, deliberately, to make that specific view-switch button stand out from the rest of the (otherwise all-`GHOST_BG`) action row |
| `GHOST_BG` / `GHOST_HOVER` | `#2a2e37` / `#343a45` | Secondary/utility buttons |
| `DANGER` / `DANGER_HOVER` | `#b91c1c` / `#991b1b` | Destructive actions (Delete, Exit) |
| `CHIP_BG` | `#2a2e37` | Version/storage chips, stat cards |
| `GOLD_BG` / `GOLD_HOVER` | `#f2c14e` / `#e0ad33` | Donate button only |
| `NOW_LINE_COLOR` | `#22c55e` | Weekly view's live "current time" line and its accompanying dot marker (v2.9.0, dot added v2.11.2) -- deliberately distinct from `ACCENT` (today/primary action) and `DANGER` (destructive), so it reads as its own unambiguous signal |

Meeting cards use a separate `_CARD_PALETTE` dict (same hues, tuned for the card background) -- don't hardcode new colors elsewhere; add a constant here if a new one is genuinely needed.

Gadget mode (v2.12.0) has its own small palette registry, `GADGET_SKINS` (right after `GADGET_MARGIN_BOTTOM`), independent of the table above -- 4 skins (`classic`/`glass`/`light`/`neon`), each a dict of `bg`/`border`/`title_fg`/`clock_fg`/`alert_fg`/`close_hover_bg`/`alpha`. `light` is the one place in the whole app with a light background (`#f5f6f8`) -- its text colors were deliberately tuned to a 7:1+ contrast ratio rather than reusing this app's existing dark-palette values, since dark-on-light has a different readability margin than the all-dark palette above. `neon`'s `clock_fg` (`#38bdf8`) is intentionally NOT `ACCENT` (`#3b82f6`) -- reusing the button/link blue read as "the normal blue," not a distinct skin; picked a brighter, more saturated blue in the same hue family instead. `glass`'s `alpha=0.90` is real window-wide translucency (`root.attributes("-alpha", ...)`, reset to `1.0` on leaving gadget mode), not a color value -- don't drop it to chase more contrast, that weakens the one thing that makes "glass" read as glass; text/border colors already carry margin against a bright desktop showing through.

## Spacing conventions

- Panel padding: `padx=14-16, pady=14-16` for outer panels; `padx=10, pady=(0,10)` between stacked form fields.
- Buttons: `padx=12, pady=6` (via `_button()`); card action buttons are slightly smaller.
- Header action row (Notificar/Idioma/view-switch/Gadget/Bandeja/Donar/Salir) is the one deliberate exception to `_button()`'s default 11pt font, via its `font_size` parameter (`_HEADER_BUTTON_FONT_SIZE=9`) -- a real, measured space conflict at the app's 960px `minsize` floor: this row's own Spanish button text plus a never-clipped `title_label` don't both fit at 11pt no matter how tight the surrounding padding gets (see SDD.md's second-round header responsiveness fix). Don't "fix" this row back to 11pt without re-measuring that constraint first.
- Use `tk.Frame(parent, bg=<matching parent bg>, width=N).pack(side="left")` as a spacer instead of ad-hoc padx bumps when you want a deliberate visual gap (see the Exit button separator in the header).

## Widget-count budget

- Header: ~10 widgets total (title, subtitle, 2 chips, 4 buttons + 1 spacer).
- Form panel: ~30 widgets (fixed, doesn't scale with data).
- Summary panel chrome: ~20 widgets (fixed).
- **Meeting card: ~10 widgets, multiplied by the number of visible meetings.** This is the one place where widget count scales with data and where a "just one more label" change has a real, measured cost (a full CustomTkinter-based card set with ~40 meetings added 20+ seconds to startup before the plain-tkinter rewrite; even plain-tk widgets have non-zero geometry-management cost at scale). Think twice before adding a widget here; prefer combining text into an existing label.
- **Calendar grid (`calendar_view`, since v2.7.0): 42 cells x 6 widgets (frame, day label, 3 entry labels, 1 overflow label) = ~250 widgets.** Fixed -- doesn't scale with data (always exactly 6 weeks x 7 days) -- and built once eagerly alongside `full_view`/`gadget_view`, never destroyed/rebuilt on a render (only `.configure()`/`.grid()`/`.grid_remove()` on the existing 42). This was the largest fixed widget cost in the app until `week_view` (below) surpassed it; it's what made the v2.4.0 5-second startup budget worth re-measuring after v2.7.0 shipped (it passed). Adding a widget per cell here multiplies by 42, not by the visible-meeting count -- treat it with the same "think twice" discipline as the meeting card, not as a fixed one-time cost like the header.
- **Weekly grid (`week_view`, since v2.9.0): 168 hour-cells x 4 widgets (frame, 2 entry labels, 1 overflow label) = ~672 widgets, plus 24 static hour-axis labels, 7 day-header labels, 1 live time-line, its own header (~10) and nav bar (~4) -- ~718 total.** The single largest fixed widget jump in the app's history (more than 2.8x the calendar grid's own ~250), built eagerly alongside `full_view`/`calendar_view`/`gadget_view` -- measured against the .exe's 5s startup budget after implementing (passed: both a "before" and "after" `.exe` build measured in the same 3.7-4.3s range, see SDD.md v2.9.0's eager-vs-lazy measurement). `WEEK_MAX_ENTRIES_PER_CELL = 2` (not the month's 3) is the deliberate mitigation already baked into the design, not an alternative to reach for later. `v2.10.0` added exactly **one** more widget to this view's nav bar (`week_column_toggle_button`, the work-week/full-week toggle) -- not 336 (the work-week mode hides 2×24 existing weekend cells via `.grid_remove()`, it never destroys/rebuilds them). `v2.11.2` added exactly **one** more widget to this view, same discipline: `_week_now_dot`, a small `tk.Canvas` "current time" marker built once alongside the existing live line and only ever `.place()`d/`.place_forget()`'d together with it, never destroyed/recreated -- a pure visual-clarity fix (thicker line + dot), not a new moving part.
- **Right-click context menu (month/week, since v2.10.0; gadget skin picker, since v2.12.0): +1 widget total for the whole app, not one per cell/mode.** A single, long-lived `tk.Menu` (`MainWindow._context_menu`), reused for every right-click across the 42-cell month grid, the 168-cell week grid, AND the gadget's skin picker -- its contents are cleared and re-added (`.delete(0, "end")` + `.add_command(...)`/`.add_radiobutton(...)`) right before each `tk_popup()` call, which is safe from the leak class below because `tkinter.Menu.delete()` itself releases each removed entry's Tcl command (confirmed against the stdlib source, unlike a plain `.bind()` re-call). Never build a `tk.Menu(...)` inside a per-cell click handler -- that would be a widget-per-click leak, a strictly worse version of the mistake this section already warns about for commands.
- **Gadget mode (v2.12.0): +2 fixed widgets** (`gadget_skin_button`, `gadget_resize_grip`), built once in `_build_gadget_view` alongside the pre-existing strip/clock/alert labels -- never rebuilt on skin switch or resize, only `.configure()`d (colors via `apply_gadget_skin`, wraplength/font live during a resize drag).

## Track record: simplifying fixed real bugs here, not just aesthetics

- Dropping CustomTkinter for plain tkinter fixed a 20+ second startup freeze (v2.0.1).
- Merging the countdown + recurrence line into one label per card reduced widget count and visual clutter at the same time (v2.1.0).
- Removing a single synchronous `update_idletasks()` call fixed the real remaining freeze (v2.1.0) -- the fix was deletion, not addition.
- Capturing and explicitly releasing the Tcl command handle (`funcid`) that `bind_all` returns, instead of trusting `unbind_all()` to release it, fixed a real +79MB RSS / 101k-orphaned-Tcl-command memory leak in `_ScrollablePanel`'s mousewheel scroll binding (v2.8.0). Not a "fewer moving parts" fix like the ones above -- it's the one case in this list that added code -- but the same underlying discipline: never assume Tk/Tcl silently cleans up after a repeated `.bind()`/`bind_all()` call on a widget that outlives the call (see `.claude/skills/timermeet-python-builder/references/module-map.md`'s standing note -- this is the second time this exact category of bug has hit the codebase, after v2.7.0's calendar-entry rebind leak).
- `v2.7.0`'s calendar-entry rebind leak above turned out to only be half-fixed: gating the re-render behind a dirty-check signature stopped *wasted* rebinds, but every genuinely-triggered rebind (a real month/week navigation) still leaked, unnoticed until a dedicated `v2.10.0` investigation used the *correct* leak metric (real interpreter-wide `info commands`, not `root._tclCommands`, which is blind to a plain `.bind()`'s command on a non-root widget -- see module-map.md). The fix is the same discipline as `_ScrollablePanel`'s above, generalized into a reusable helper, `main_window._rebind(widget, sequence, handler, previous_funcid)`, now used by every rebind site in `_update_calendar_cell`/`_update_week_cell` (including the new right-click bindings) -- any future code that repeatedly `.bind()`s a long-lived widget should call this instead of `.bind()` directly, not reinvent the capture-and-release logic per call site.

When in doubt, the direction that has actually worked in this project is *fewer moving parts*, not more visual polish layered on top -- and where a widget does need repeated re-binding (calendar cells, scroll panels), don't assume the framework releases what it registered.

## Reusable pattern: a `weight=1` grid column can collapse to ~0px next to a `weight=0` sibling -- give it a real `minsize` floor

Discovered in `v2.9.0`'s header responsiveness fix, but the underlying Tk behavior is general and will recur anywhere a "flexible label column next to a fixed-width button row" layout exists: `grid_columnconfigure(0, weight=1)` alone does **not** protect column 0's content from shrinking arbitrarily -- Tk always gives a `weight=0` sibling column its full requested width first and shrinks the `weight=1` column to absorb any deficit, all the way to 0px if needed. This is what let `title_label` ("TimerMeet" itself) render at ~1px wide at the app's own 960px `minsize` floor before the fix, and it depended on construction history (hysteresis: a window built at 1180px then resized down to 960px rendered differently than one built at 960px directly), because an unset `minsize` derives column 0's "natural" width from its own content, which itself depends on the most recent layout pass.

**The fix, as a reusable two-part recipe (see `_header_title_column_minsize`/`_truncate_text_to_pixel_width` in `main_window.py`):**
1. **Give the flexible column a real, measured `minsize` floor** -- computed via `tkinter.font.Font.measure()` against the actual text/font of whatever must never fully disappear (plus its own padding), not a guessed constant. A static, measured number also kills the hysteresis for free: there's no "history" a fixed number can depend on.
2. **Let the next-most-important sibling (the subtitle, not the title) truncate dynamically with an ellipsis instead** -- via `_truncate_text_to_pixel_width` (binary search against `font.measure()`, not a fixed character count like the calendar/week grids use, because this column's available width genuinely changes on every resize). Recompute on every real `<Configure>` of the header, debounced via `after_idle` (same pattern `_ScrollablePanel` already established for its own `<Configure>` bursts), and also on language change (`apply_translations`, since `es`/`en` strings differ in length). Never add a separate "hide below N px" special case -- an empty string from the same truncation call already covers that.

Don't reach for `wraplength` as a first attempt here: a fixed `wraplength` forces wrapping at every window size, not just narrow ones, which silently grows the header's height everywhere and can break unrelated layouts sized against a single-line header (this broke 6 calendar-grid tests in `v2.9.0`'s first attempt, reverted before shipping).

## Reusable pattern: keep a stretchy label's `wraplength` in sync with its actual container width, don't hardcode it

`MEETING_CARD_MAX_WIDTH_PX` (above) caps how wide a meeting card can grow, but capping the container without also updating what's *inside* it just moves the clipping problem from "the whole card" to "the title label inside it" -- a title near `security.MAX_TITLE_LENGTH` (120 chars) silently clipped mid-character once the card stopped growing to fit it (`v2.9.0`). The fix: `_ScrollablePanel` gained an optional `on_content_width_change(width: int)` callback, fired from `_update_canvas_width` every time the resolved (post-`max_content_width`) width actually changes -- a caller whose children need to track that width (e.g. a card title's `wraplength`) subscribes here instead of adding its own second `<Configure>` binding on `.body` (which would silently clobber `_ScrollablePanel`'s own existing scrollregion binding unless it remembered `add="+"`). The meeting list uses this (`_on_meeting_list_width_change`) to keep every visible card's `title_label.wraplength` equal to `width - 2*padx`, including cards created after the first resize (seeded with the last known width in `_create_card`). Prefer wrapping over truncation for content whose height is already flexible elsewhere (a card, not a fixed-height calendar cell) -- `_ScrollablePanel` already recomputes its `scrollregion` from real content on every change, so a taller wrapped card costs nothing extra to accommodate.
