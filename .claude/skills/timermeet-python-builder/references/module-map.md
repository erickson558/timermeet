# TimerMeet Python module map

| File | Owns | Don't put here |
|---|---|---|
| `timermeet_app/models.py` | `Meeting` dataclass, `normalize_meeting()`, `validate_meeting()` | UI text, persistence |
| `timermeet_app/recurrence.py` | Occurrence generation (`add_recurrence_to_date`), the Friday-18:00 weekly renewal engine (`run_weekly_series_renewal`) | Persistence, UI |
| `timermeet_app/retention.py` | Two cleanup functions: `purge_stale_meetings` (automatic, conservative -- 7-day grace, only fully-alerted) and `clear_past_meetings` (manual "delete past events" button -- immediate, ignores alert flags). Both always keep each series' latest occurrence | Persistence, UI, anything about *when* an alert fires (that's `app.py`) |
| `timermeet_app/storage.py` | Atomic JSON read/write, the same-machine advisory lock, merge-on-save (`merge_meeting_lists`/`merge_meeting_pair`), settings persistence (language, company list -- `load_companies`/`save_companies`, local to this machine, not merged like meetings) | Business rules about *when* to fire an alert (that's `app.py`) |
| `timermeet_app/audio.py` | The 5 sound profiles, MP3 playback via Windows MCI (`winmm.dll` through `ctypes`) with `winsound.Beep` synth fallback | UI widgets |
| `timermeet_app/notifications.py` | Best-effort native OS toast via `plyer` | Anything load-bearing -- this must never be relied on as the only alert channel |
| `timermeet_app/alarm_ui.py` | The persistent alarm overlay + title-bar blink (`AlarmController`) -- a single on-screen alert window at a time, backed by a FIFO queue (`self._queue`, since v2.7.1): if a second alert becomes due while one is already showing, it's queued and auto-presented (`_present`) the moment the current one is dismissed, never dropped or stacked on top | Business logic about which meeting fires next (that's `app.py`) |
| `timermeet_app/tray_icon.py` | System tray icon (`TrayIcon`, built on `pystray`, imported lazily). Every callback it fires runs on pystray's own background thread -- callers (app.py) must wrap them in `root.after(0, ...)` before touching any Tkinter widget | Tkinter widget code, business logic |
| `timermeet_app/main_window.py` | All widget construction and rendering (`MainWindow`) -- view layer only. Three mutually-exclusive sibling frames share the same `root` grid cell, swapped via `set_active_view`/`set_gadget_mode` (never a second `Tk()`/`Toplevel`): the normal list view, the gadget/skin mode (`set_gadget_mode`, `_build_gadget_view` -- reskins the same `root`), and the monthly calendar view (since v2.7.0: `_build_calendar_view`, `render_calendar`, all 42 day cells built once eagerly and reused via `.configure()`/`.grid()`). `_ScrollablePanel` is the shared mousewheel-scroll wrapper used by both the form and meeting-list panels -- see the Tcl-command-leak note below before touching its `<Enter>`/`<Leave>` handling | Validation, persistence, stats computation |
| `timermeet_app/app.py` | The controller: heartbeat (`root.after` every 1s), alert firing gate, stats/next-alert computation, save/edit/delete handlers, resync-from-disk | Widget construction |
| `timermeet_app/i18n.py` | ES/EN translation dict, `t()`/`format_text()` | Anything not a translated string |
| `timermeet_app/security.py` | `is_http_url()`, `clamp_text()`, `atomic_write_text()`, the field-length constants | Anything unrelated to input safety/file safety |

When in doubt about where new logic belongs: business rules and computed state go in `app.py`; anything about one meeting's shape/validity goes in `models.py`; anything about the on-disk representation goes in `storage.py`; anything the user sees goes in `main_window.py` (rendered) driven by `i18n.py` (translated).

## Recurring footgun: repeated `.bind()`/`bind_all()` on a long-lived widget leaks Tcl commands

This codebase has hit the same root cause twice now, in two different versions, on two different binding mechanisms: **a repeated `.bind()`/`bind_all()` call on the same widget+sequence does not release the previously-registered Tcl command on this Tk/Python version** -- verified directly both times, not assumed.

- **v2.7.0**, calendar entry labels (`_update_calendar_cell`): `render_calendar` re-bound `.bind("<Button-1>", ...)` with a fresh closure on every visible entry on every 1s heartbeat tick while the calendar view was open -- confirmed directly (2000 rebinds left 2000 orphaned entries in `widget._tclCommands`, growing unbounded). The rebind itself is legitimate here (a calendar cell is a fixed grid *position*, not a fixed date -- the meeting it should open on click changes every time the user navigates months, so it can't just bind once at construction). **Fix used:** gate the re-render/re-bind behind a dirty-check signature (`_last_rendered_calendar_signature` in `app.py`) so `_update_calendar_cell` -- and its `.bind()` calls -- only run when that cell's actual displayed content changed, not on every idle heartbeat tick.
- **v2.8.0**, `_ScrollablePanel`'s mousewheel scoping: `<Enter>`/`<Leave>` called `self.canvas.bind_all("<MouseWheel>", ...)`/`unbind_all(...)` on every hover in/out of the form or meeting-list panel -- here there is no "content changed" signature to gate on (every real mouse hover is a legitimate re-bind), so the v2.7.0 fix doesn't apply. `unbind_all` only removes Tk's binding entry for that sequence -- it never releases the Tcl command `bind_all` registered. Measured over 100,000 realistic enter/leave cycles: +79MB RSS, 101k orphaned commands. **Fix used:** capture the identifier `bind_all` returns (a `funcid`) in `_bind_wheel`/`_unbind_wheel` and explicitly release the underlying Tcl command with `deletecommand` on `<Leave>`, instead of trusting `unbind_all` to clean it up. Note the identifier is tracked against the **root widget** (`self._root()`), not the widget `bind_all()` was called on -- releasing it against the wrong widget object leaves a dangling name in the root's own cleanup bookkeeping (`root.destroy()` raising `TclError` was how this was caught).

Two different fixes (skip the re-bind when nothing changed vs. capture-and-release the funcid) because the two cases differ in whether "don't re-bind unless something changed" is available -- but the same root cause both times. **Any future code that repeatedly calls `.bind()` or `bind_all()`/`bind_class()` on a widget that is never destroyed between calls (a long-lived cell, panel, or canvas re-rendered on a timer or on every hover/every render) should be checked for this pattern proactively while writing it** -- either gate the rebind behind a real change, or capture and release the funcid -- rather than relying on an adversarial review to catch it after the fact, as happened both times above.
