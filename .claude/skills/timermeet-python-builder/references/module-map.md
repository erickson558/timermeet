# TimerMeet Python module map

| File | Owns | Don't put here |
|---|---|---|
| `timermeet_app/models.py` | `Meeting` dataclass, `normalize_meeting()`, `validate_meeting()` | UI text, persistence |
| `timermeet_app/recurrence.py` | Occurrence generation (`add_recurrence_to_date`), the Friday-18:00 weekly renewal engine (`run_weekly_series_renewal`) | Persistence, UI |
| `timermeet_app/retention.py` | Two cleanup functions: `purge_stale_meetings` (automatic, conservative -- 7-day grace, only fully-alerted) and `clear_past_meetings` (manual "delete past events" button -- immediate, ignores alert flags). Both always keep each series' latest occurrence | Persistence, UI, anything about *when* an alert fires (that's `app.py`) |
| `timermeet_app/storage.py` | Atomic JSON read/write, the same-machine advisory lock, merge-on-save (`merge_meeting_lists`/`merge_meeting_pair`), settings persistence (language, company list -- `load_companies`/`save_companies`, local to this machine, not merged like meetings) | Business rules about *when* to fire an alert (that's `app.py`) |
| `timermeet_app/audio.py` | The 5 sound profiles, MP3 playback via Windows MCI (`winmm.dll` through `ctypes`) with `winsound.Beep` synth fallback | UI widgets |
| `timermeet_app/notifications.py` | Best-effort native OS toast via `plyer` | Anything load-bearing -- this must never be relied on as the only alert channel |
| `timermeet_app/alarm_ui.py` | The persistent alarm overlay + title-bar blink (`AlarmController`) -- a single on-screen alert window at a time, backed by a FIFO queue (`self._queue`, since v2.7.1): if a second alert becomes due while one is already showing, it's queued and auto-presented (`_present`) the moment the current one is dismissed, never dropped or stacked on top | Business logic about which meeting fires next (that's `app.py`) |
| `timermeet_app/tray_icon.py` | System tray icon (`TrayIcon`, built on `pystray`, imported lazily). Every callback it fires runs on pystray's own background thread -- callers (app.py) must wrap them in `root.after(0, ...)` before touching any Tkinter widget | Tkinter widget code, business logic |
| `timermeet_app/main_window.py` | All widget construction and rendering (`MainWindow`) -- view layer only. Four mutually-exclusive sibling frames share the same `root` grid cell, swapped via `set_active_view`/`set_gadget_mode` (never a second `Tk()`/`Toplevel`): the normal list view, the gadget/skin mode (`set_gadget_mode`, `_build_gadget_view` -- reskins the same `root`), the monthly calendar view (since v2.7.0: `_build_calendar_view`, `render_calendar`, all 42 day cells built once eagerly and reused via `.configure()`/`.grid()`), and the weekly calendar view (since v2.9.0: `_build_week_view`, `render_week_grid` (Nivel A, data-driven, does the `.bind()` rebinding) + `update_week_live_indicators` (Nivel B, clock-driven, `.configure()`/`.place()` only, never `.bind()`) -- see this file's "Recurring footgun" note below, which this split exists specifically to avoid a third time). `_ScrollablePanel` is the shared mousewheel-scroll wrapper used by the form, meeting-list, and weekly-grid panels -- see the Tcl-command-leak note below before touching its `<Enter>`/`<Leave>` handling | Validation, persistence, stats computation |
| `timermeet_app/app.py` | The controller: heartbeat (`root.after` every 1s), alert firing gate, stats/next-alert computation, save/edit/delete handlers, resync-from-disk | Widget construction |
| `timermeet_app/i18n.py` | ES/EN translation dict, `t()`/`format_text()` | Anything not a translated string |
| `timermeet_app/security.py` | `is_http_url()`, `clamp_text()`, `atomic_write_text()`, the field-length constants | Anything unrelated to input safety/file safety |

When in doubt about where new logic belongs: business rules and computed state go in `app.py`; anything about one meeting's shape/validity goes in `models.py`; anything about the on-disk representation goes in `storage.py`; anything the user sees goes in `main_window.py` (rendered) driven by `i18n.py` (translated).

## Recurring footgun: repeated `.bind()`/`bind_all()` on a long-lived widget leaks Tcl commands

This codebase has hit the same root cause three times now, in three different versions: **a repeated `.bind()`/`bind_all()` call on the same widget+sequence does not release the previously-registered Tcl command on this Tk/Python version** -- verified directly every time, not assumed.

**⚠️ Methodology correction (found in the same investigation that produced the v2.10.0 entry below) -- read this before writing or trusting ANY leak-regression test for a plain (non-`bind_all`) `.bind()`:** `root._tclCommands` (the metric `tests/test_scrollable_panel.py` uses for the v2.8.0 `bind_all()` case, correctly) is **blind** to a leak from a plain `.bind()` call on any widget other than root. Confirmed empirically: 500 leaked plain-`.bind()` Tcl commands on a `tk.Frame` moved `len(root._tclCommands or [])` by exactly **0**, while the real interpreter-wide count (`len(root.tk.splitlist(root.tk.call("info", "commands")))`) moved by exactly **500**. This is because a plain (non-`"all"`) `.bind()` registers its funcid via `self._register()` against the WIDGET ITSELF's own `_tclCommands` bookkeeping, never root's -- the opposite of `bind_all()`, which (per the v2.8.0 entry below) always routes through `self._root()`. **Any prior or future "confirmed leak-free" claim for a plain `.bind()` case that only checked `root._tclCommands` could not have caught a real leak.** Use `tests/testutils.py::count_tcl_commands()` (`info commands`) instead for any plain-`.bind()` leak test; `root._tclCommands`-based assertions for genuine `bind_all()` cases (`tests/test_scrollable_panel.py`) remain correct and don't need to change.

- **v2.7.0**, calendar entry labels (`_update_calendar_cell`): `render_calendar` re-bound `.bind("<Button-1>", ...)` with a fresh closure on every visible entry on every 1s heartbeat tick while the calendar view was open -- confirmed directly (2000 rebinds left 2000 orphaned entries in `widget._tclCommands`, growing unbounded). The rebind itself is legitimate here (a calendar cell is a fixed grid *position*, not a fixed date -- the meeting it should open on click changes every time the user navigates months, so it can't just bind once at construction). **Fix applied at the time:** gate the re-render/re-bind behind a dirty-check signature (`_last_rendered_calendar_signature` in `app.py`) so `_update_calendar_cell` -- and its `.bind()` calls -- only run when that cell's actual displayed content changed, not on every idle heartbeat tick. **This fix was incomplete, and the gap went undetected until v2.10.0 (see that entry below):** gating only stops *wasted* rebinds when nothing changed -- it does nothing about the Tcl command a real, correctly-triggered rebind (a month navigation, an edit, a language toggle) still leaves behind every time it fires. The leak was smaller and slower after this fix (bounded by how often the user actually navigates/edits, not by the heartbeat), but still unbounded over a long-running session -- exactly the kind of session this app is designed for.
- **v2.8.0**, `_ScrollablePanel`'s mousewheel scoping: `<Enter>`/`<Leave>` called `self.canvas.bind_all("<MouseWheel>", ...)`/`unbind_all(...)` on every hover in/out of the form or meeting-list panel -- here there is no "content changed" signature to gate on (every real mouse hover is a legitimate re-bind), so the v2.7.0 fix doesn't apply. `unbind_all` only removes Tk's binding entry for that sequence -- it never releases the Tcl command `bind_all` registered. Measured over 100,000 realistic enter/leave cycles: +79MB RSS, 101k orphaned commands. **Fix used:** capture the identifier `bind_all` returns (a `funcid`) in `_bind_wheel`/`_unbind_wheel` and explicitly release the underlying Tcl command with `deletecommand` on `<Leave>`, instead of trusting `unbind_all` to clean it up. Note the identifier is tracked against the **root widget** (`self._root()`), not the widget `bind_all()` was called on -- releasing it against the wrong widget object leaves a dangling name in the root's own cleanup bookkeeping (`root.destroy()` raising `TclError` was how this was caught).

Two different fixes (skip the re-bind when nothing changed vs. capture-and-release the funcid) because the two cases differ in whether "don't re-bind unless something changed" is available -- but the same root cause both times, and (see v2.10.0 below) the first of those two fixes turned out not to be the full story. **Any future code that repeatedly calls `.bind()` or `bind_all()`/`bind_class()` on a widget that is never destroyed between calls (a long-lived cell, panel, or canvas re-rendered on a timer or on every hover/every render) should be checked for this pattern proactively while writing it** -- gating a rebind behind a real change is necessary to avoid *wasted* work, but it is NOT sufficient on its own; a real, correctly-triggered rebind must ALSO capture-and-release the previous funcid (`_rebind()` in `main_window.py` is the reusable helper for this, added in v2.10.0) -- rather than relying on an adversarial review to catch a gap, as happened above.

- **v2.9.0**, the weekly view's live "now" time-line: this one was designed up front (in SDD.md, before any code) specifically to avoid a third hit of this exact bug class. The naive approach -- re-bind the 168 hour-cells' click handlers in the *same* function that also repositions the per-minute time-line -- would force a `.bind()` rebind pass every minute forever, purely from the clock ticking, exactly like v2.7.0's mistake just 60x less frequent (still unbounded over a long-running session). **Fix used (by design, not after the fact):** two independent functions/signatures -- `render_week_grid` (Nivel A, gated by a signature with NO hour/minute component, does all the `.bind()` calls) and `update_week_live_indicators` (Nivel B, gated by its own `(today_index, hour, minute)` tuple, only ever calls `.configure()`/`.place()`/`.place_forget()`, never `.bind()`). Verified directly: 1000 repeated calls to `update_week_live_indicators` (500 with an unchanging minute, 500 with the minute varying) leave the root's Tcl command count exactly unchanged -- correctly so here, since Nivel B never calls `.bind()` at all, so there is nothing for the `root._tclCommands`-vs-`info commands` distinction above to matter for this specific measurement.
- **v2.10.0**, `_update_calendar_cell`/`_update_week_cell`, for real this time: a dedicated investigation (using the corrected `info commands` metric above, which the v2.7.0 fix was never re-checked against) proved the v2.7.0 gating fix left every REAL re-render still leaking one Tcl command per rebound widget (`day_label`/`frame`/each visible `entry_label`, both `<Button-1>` and, once added this same version, `<Button-3>` for the new context menu) -- measured directly against real navigation (`TimerMeetApp.handle_week_next()`/`handle_calendar_next_month()`, not just calling the render function in isolation), with `_rebind()` itself monkeypatched back to a naive, non-releasing `.bind()` so the CURRENT binding set (including the `<Button-3>` context-menu bindings this same version adds) is what gets measured, not an older/smaller one: 200 real week-view navigations (168 cells, only the frame's `<Button-1>`/`<Button-3>` background bindings -- no meeting entries present, so no `entry_label` bindings counted) leaked exactly +67,200 Tcl commands (336 per call -- 168 cells x 2 background bindings); 200 real month-view navigations (42 cells, `day_label` + `frame` each getting `<Button-1>`/`<Button-3>` = 4 bindings/cell) leaked exactly +33,600 (168 per call -- 42 cells x 4 bindings). Both figures scale linearly and unboundedly with call count, and both match SDD.md's own re-measurement of this identical scenario -- keep the two documents in sync if either number is ever re-measured again. **Fix used:** `_rebind(widget, sequence, handler, previous_funcid)`, a small reusable helper that calls `widget.deletecommand(previous_funcid)` (confirmed empirically to be the WIDGET itself, not `widget._root()` -- the opposite of `bind_all()`'s case above, since a plain `.bind()`'s funcid was never in root's own bookkeeping to begin with) before rebinding. Both cell dataclasses (`_CalendarCellWidgets`/`_WeekCellWidgets`) gained a `bind_funcids: Dict[str, Optional[str]]` field to track each widget+sequence pair's current funcid across renders. Verified with `info commands`: repeated real re-renders (via actual month/week navigation, not just calling the render function with unchanged data) now leave the count bounded instead of growing per re-render.
